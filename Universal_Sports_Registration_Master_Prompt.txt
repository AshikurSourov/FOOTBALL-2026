6. STRICT DUPLICATE PROTECTION
This is a critical requirement.

Registration ID:
- Every registration must have a unique, server-generated Registration ID.
- Enforce uniqueness with a database UNIQUE constraint.
- Never allow public clients to choose or overwrite Registration IDs.
- Use collision-safe ID generation and retry on a database uniqueness conflict.
- Ensure concurrent requests cannot create duplicate Registration IDs.
- Support idempotency keys for repeated submissions where appropriate.
- A retry after a timeout must not silently create a second registration for the same idempotent request.

Player ID:
- Each player record has a unique Player ID.

Phone number policy:
- The same phone or WhatsApp number may be used for multiple registrations where allowed.
- Do not impose a global unique constraint on phone number.
- A player may register for different events using the same phone number.
- Detect possible repeated registrations within the same event using configurable checks and admin review.
- Do not assume that two people with the same phone number are necessarily the same person.
- Do not block unrelated registrations solely because their contact numbers match.

Maintain duplicate-detection logs and explain rejected submissions clearly.

Use transactions and database constraints as the final protection layer, not just frontend JavaScript.
